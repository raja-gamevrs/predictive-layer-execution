Research log · 23–25 November 2026 · one RTX 5090

Making LLMs write faster: what failed, what worked

We set out to speed up language models by guessing each layer's output ahead of time. That idea failed every test. Measuring where the time really goes led somewhere better: a set of exact changes to the decoding step that make today's popular open models write faster, with the same output as the model itself, and on equal weights faster than or level with llama.cpp.

Everything below is in the order it happened. Every number is read from a result file in the repository (raja-gamevrs/predictive-layer-execution, results/processed/). Exact means the output is the model's own greedy text: we re-run the model over what the engine wrote and count "violations", tokens where the engine picked something other than the model's clear first choice. Tokens per second is the steady writing speed, prompt reading not counted. One user at a time (batch 1), greedy decoding, Windows.

Chapter 1 · 23 November

Where we started: guess the next layer

A language model is a tall stack of layers, and each layer waits for the one below it. Our idea, "Predictive Layer Execution" (PLE): guess what a layer will output, start the next layers early on the guess, then fix the small difference when the real output arrives. If the guess is good and the fix is cheap, layers overlap and the same answer comes out sooner.

We wrote six hypotheses down before running anything:

HypothesisIn plain wordsOutcome
H1A layer's change is predictable from what came beforeOnly roughly
H2The guessing error has a simple shape we can exploitNo
H3Fixing the error is cheaper than computing the layerNo
H4Running the guess in parallel shortens each tokenA little
H5It works better on reading the prompt than on writingNo
H6A smart policy (when and where to guess) beats always guessingNot enough

Models: Qwen3-4B, Qwen3.5-4B, Ornith-1.5-9B, Qwen3.8-27B. Text: WikiText-2, held-out split untouched.

Chapter 2 · 23–24 November

What we found: guessing layers does not pay

  • Guesses are rough. The best cheap guess (a linear map) is still … wrong on Qwen3-4B. Guessing "nothing changes" is … wrong; smarter extrapolation is worse (…).
  • Fixing is not cheap. Spending a quarter of a layer's cost on the worst channels still leaves … error. The error is spread everywhere.
  • Skipping the fix hurts quality. Guess every layer with the linear map and perplexity goes from … to … (Qwen3-4B); with the naive guess, to ….
  • The GPU barely overlaps the work. For one token at a time the most a guessed layer could save is …; we measured …, and nothing for long inputs (… at 2,048 tokens).
  • Removing parts outright (Phase II): within a 1% perplexity budget only … of the compute can go. The goal was 10%.
  • Five rescue attempts (E1–E5): the best decode speed-up was …, and only by guessing every layer in FP8, which breaks quality. A per-token gate, LoRA "healing" (stops at …× the quality bar) and a trained predictor (…× the error of plain ridge regression) each fell short.
  • Skipping layers to make a draft keeps the output exact, but a draft with 26% of layers skipped still costs … of a full step, so the best setting runs at …: slower than not trying.

Lesson: modern LLM layers are not redundant enough to guess cheaply, and at one user at a time the GPU cannot hide the extra work.

Chapter 3 · 23 November

A useful side finding: what stays exact under quantization

When we fixed a guess exactly, the answer stayed exact only if the weights were quantized and the activations stayed 16-bit (INT8, NVFP4 W4A16, Red Hat's Qwen3.8 INT4). Rounding activations too (FP8 W8A8, NVFP4 W4A4) broke it. That is why our engine later keeps activations in BF16.

Chapter 7 · 24–25 November

Real-world lengths, and a fair fight with llama.cpp

Real use means quantized models and long conversations, not 16-bit weights and short prompts. So we made the comparison fair:

  • Same weights, byte for byte. We re-implemented llama.cpp's 8-bit format (Q8_0; every byte checked against llama-quantize) and wrote our 4-bit draft codes and Red Hat's Qwen3.8 INT4 codes into GGUF files, so llama.cpp runs exactly our numbers.
  • Same KV cache (BF16) in both; YaRN for Qwen3-4B above 32k in both.
  • 7 context lengths, 2k to 128k tokens, steady speed only, 2 timed runs each.

Chapter 8 · 25 November

8-bit models, and why 2-bit drafts are a dead end

Most people run quantized models, so the target became 8-bit (Q8_0) for Qwen3-4B and Gemma 4 12B, with our own 8-bit kernel (Triton). The 8-bit Qwen3-4B runs about 1.6× faster than BF16. But at 8 bits the 4-bit draft helps less: a draft step costs about two thirds of a target step, because ~0.9 ms of every step is thousands of tiny kernels that do not shrink with the weights. That pointed to chapter 9.

Could a 2-bit draft be cheap enough? We tried it in llama.cpp first. It needs to be right about 75% of the time; it was not:

Chapter 9 · 25 November

Fusing thousands of tiny kernels

Each token launched 655 small GPU kernels on Qwen3-4B, 3,039 on Gemma 4 12B and 4,940 on Qwen3.8. Compiling the whole step with torch.compile was slower: it turned every KV-cache write into a copy of the whole cache. Compiling only the small pure pieces (norm + residual, q/k norm + rotary step, activations, Gemma's softcap, Qwen3.8's whole recurrent DeltaNet update) worked. Gemma went from 3,039 to 1,205 kernels per token.

Chapter 10 · 25 November

Qwen3.8's own draft: its multi-token-prediction layer

Qwen3.8 is already 4-bit, so a 4-bit copy of itself is no cheaper. But it ships with a small extra layer trained to guess the next-next token: multi-token prediction (MTP). One MTP step costs one layer plus the output head instead of 64 layers. We use it as the draft: it guesses k tokens, the full model checks them in one pass, and the whole round (guess, check, accept, roll the recurrent DeltaNet state back to the last kept token) is one CUDA graph.

A bug found by comparing with llama.cpp. Our first version fed the MTP layer the model's hidden state before its final normalization; llama.cpp's MTP on the same file was accepted more often (86% against 79% at 2k) and ran faster. Its code feeds the state after the norm, as the model was trained. We fixed it, reran every context, and kept the first run on file.

At 2k context Qwen3.8 now writes … tokens/s with its MTP draft against … without it, with the model's own output (0 violations for every k tried). llama.cpp's own MTP on the same weights reaches …. With only the bug fixed we were at 150, a little behind: the drafts were accepted equally often in both engines, so llama.cpp's round was cheaper. The next step closed that. Hover the Qwen3.8 chart in chapter 12 for every context.

The last step: a 4-bit output layer for the draft only. Every MTP guess reads Qwen3.8's whole output layer (2.5 GB in 16-bit). We gave the draft a 4-bit copy (0.6 GB); the full model still checks every token with the real layer, so the output does not change (0 violations), and the draft is right just as often. Written down as follow-up H2 before it ran. It made the MTP round 8–17% cheaper and put us ahead of llama.cpp's own MTP at 2k, 4k, 16k, 32k and 128k (best k), 2–6% behind at 8k and 64k. The numbers above use it (k = 4).

How often a draft is right depends heavily on the text (87% on the 2k prompt, about 50% on the 8k one), in both engines. One prompt per context length. The 128k run spilled about 0.2 GB of GPU memory into system RAM and may read low.

Chapter 11 · 25 November

Inkling 2 Mini

Thinking Machines' Inkling 2 Mini (released 20 November) is a different design: a mixture of experts (128 small expert networks, 8 used per token), a block of layers that runs three times in a loop, mostly sliding-window attention, and 4-bit NVFP4 expert weights. Our decoders do not run it; porting it is a project of its own. So we measured it in llama.cpp only (b12720, converted with llama.cpp's own converter, quantized to Q4_K_M, the most common way people run GGUF models). The text it writes is coherent, but there is no exactness check without a reference implementation on this GPU.

At 128k, llama.cpp's default prompt batch needed 12.9 GB of scratch memory; with a smaller batch (-ub 128) it fits. That changes prompt reading only, not the writing speed.

Chapter 13

What helped, what did not

Helped (exact, measured)

  • A CUDA-graph decode step with fast attention and a fused rotary step.
  • Fusing the many tiny kernels: biggest on models with many small operations (Qwen3.8, Gemma).
  • The model's own 4-bit copy as a draft, with the whole round in one GPU graph: big on 16-bit targets, smaller on 8-bit, short context only.
  • Matching llama.cpp's 8-bit format exactly: about 1.6× over BF16, and a fair comparison.

Did not help

  • Guessing layer outputs (the original idea), in every form tried.
  • Skipping layers as a draft.
  • 2-bit drafts.
  • Compiling the whole step at once.
  • Self-drafts at long context with an 8-bit target.

Limits

  • One GPU (RTX 5090), Windows, one user at a time, greedy decoding, base models.
  • llama.cpp runs everywhere; ours is a research decoder for a few model families.
  • One prompt per context length for the long runs, 2 timed runs each.

What is new

Running layers early or in parallel is already published (Layer Parallelism, CQIL, EasySpec, InfiniGen), as are ridge predictors standing in for later layers (RidgeFill) and predict-then-correct schemes (SNLP). New here: the precision result above, measuring error after the next block's norm, the negative result on correction cost, and the finding that single-GPU overlap helps only at decode-sized inputs. Phase II's layer removal and replacement follow ShortGPT, Gromov et al., SLEB and LaCo; per-token depth follows CALM, LayerSkip and Mixture-of-Depths; budgeted sensitivity follows HAWQ-V3. Its candidate openings are per-operation sensitivity in hybrid linear and softmax attention models and a measured test of additivity. The name PLE also collides with Gemma's Per-Layer Embeddings.

Decode levers: every one is a known technique

None of the decode levers is new; each reimplements a published or widely shipped technique. Every speedup on this page is against this repository's own CUDA-graph decoder, not a production engine, and no production engine was measured. vLLM and FlashInfer-based servers already ship most of these levers, so the gains are not gains over them. The INT4 self-draft's 2.1–2.25× over the original decoder is in the range the self-speculation papers below report, on a different decoder and GPU.

Definitions
Projection error
Relative error at the next block's attention input projections, measured after that block's norm, between the predicted and the true input.
KL divergence, top-1 agreement
How far the speculated model's next-token distribution is from the unspeculated model's, and how often both pick the same top token.
BF16 floor
Exact correction computes the same output along two mathematically equal paths. In BF16 the rounding differs slightly, giving a small nonzero KL. Exactness is judged against this floor, not against zero.
W8A16, W4A4 and similar
Bits for weights (W) and activations (A). W4A16 quantises weights only; W4A4 and W8A8 quantise activations too.
Compute removed
Share of the decoder's multiply-accumulates per token that an operation no longer runs, net of the linear stand-in's own cost.
Calibration and holdout text
Two disjoint sets of WikiText-2 train chunks, both separate from the chunks the stand-ins were fitted on. Greedy sets are chosen on calibration text and re-measured on holdout text.
Speculative branch
The early, guessed computation of the next layer's projections, run on a second GPU stream while the current layer finishes. In FP8 it reads half the weight bytes.
Per-token gate
After the true input is known, tokens whose guess was far off (relative error above a threshold) use the exact projection instead.
Identity and linear predictors
Identity reuses the current hidden state as the next layer's input. Linear fits a ridge regression from one state to the next.
